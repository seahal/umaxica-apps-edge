# The Edge → Rails proxy trust boundary

Normative for `{app,com,org}/core/src/lib/core-dispatch.ts` and the two modules
it composes. The decision record is
[ADR 023](../../adr/023-rails-proxy-trust-boundary.md); this page is the
operational reference — what the contract is, and what you must not do to it.

The three Cores are one implementation in three copies
(`test/core-dispatch-contract.test.ts` enforces that). A change to any rule here
is a change to all three.

## 1. Client IP

```text
Browser
  ↓
Cloudflare
  sets CF-Connecting-IP
  ↓
Edge  (core-dispatch.ts + client-ip.ts)
  reads CF-Connecting-IP, and nothing else
  validates it as exactly one IPv4 or IPv6 literal
  deletes every client-identity header from the outbound request
  writes X-Forwarded-For: <that one validated address>
  ↓
Rails
  request.remote_ip
```

### Rules

**`CF-Connecting-IP` is the only authority.** It is the only header Edge reads a
client IP from. Do not add a second source, a preference order, or an override.

**The value is validated, not trusted.** Exactly one address. Rejected:
comma-separated lists, `host:port`, bracketed literals, zone ids (`%eth0`),
hostnames, leading-zero octets (`203.0.113.010` — ambiguous between parsers),
empty strings, NUL, and anything with a control character. Rejection is total:
the value is not trimmed, split, or repaired into shape.

**Every client-identity header is removed before the request leaves Edge**,
including `CF-Connecting-IP` itself — it is Edge's input, not Rails'. The full
list lives in `UNTRUSTED_CLIENT_IP_HEADERS`; it currently covers `Forwarded`,
`X-Forwarded-For`, `X-Real-IP`, `Client-IP`, `X-Client-IP`,
`X-Cluster-Client-IP`, `True-Client-IP`, `CF-Connecting-IP`,
`CF-Connecting-IPv6` and `CF-Pseudo-IPv4`.

That list is a belt on top of the braces, not the mechanism. The mechanism is
that Rails' only client-identity input is regenerated by Edge — which is why a
name missing from the list is no longer a vulnerability the way it was under the
old deny-list spelling.

**`X-Forwarded-For` is replaced, never appended to.** Edge writes exactly one
address. There is no chain, so nothing downstream needs to walk one.

**There is no fallback.** When `CF-Connecting-IP` is absent or does not validate,
Edge writes no `X-Forwarded-For` at all. Do not add a fallback to another header,
to a peer address, to `127.0.0.1`, or to a placeholder string.

A fabricated client IP is worse than an absent one: Rails cannot tell it from a
real one, so it would silently poison `request.remote_ip`, every audit record
derived from it, and every per-IP decision — most reliably in exactly the cases
where the true value was unavailable.

This is _not_ a request rejection, deliberately. The existing Edge ingress
contract already tolerates a missing `CF-Connecting-IP` — `rate-limit.ts` buckets
such requests per-path rather than refusing them, because `vite dev`,
`vite preview` and the Hurl `test:api` harness all reach the Worker without
Cloudflare in front. Rejecting would change that ingress contract. The
fail-closed behaviour is narrower: Edge declines to make a claim it cannot
substantiate, and Rails falls back to the peer address.

### On the Rails side

Use `request.remote_ip`. It is derived by `ActionDispatch::RemoteIp` from
`X-Forwarded-For` and the peer address, which is exactly what this contract
produces.

Do **not** read a header directly as a client-identity authority:

```ruby
# Never. Edge does not forward these, so they are nil — but the failure mode of
# reintroducing one is silent, which is why the rule is written down.
request.headers["True-Client-IP"]
request.headers["X-Real-IP"]
request.headers["X-Client-IP"]
```

Do **not** widen `config.action_dispatch.trusted_proxies` for this. Edge sends
one address; there is no chain for a trust range to walk, so a wider range buys
nothing and weakens the boundary.

## 2. Request body ceiling

`MAX_RAILS_REQUEST_BODY = 8 * 1024 * 1024` (8,388,608 bytes), uniform across
every Rails-owned path.

| Case                                                                   | Answer                                 |
| ---------------------------------------------------------------------- | -------------------------------------- |
| Declared `Content-Length` ≤ 8 MiB                                      | relayed                                |
| Declared `Content-Length` > 8 MiB                                      | **413**, before any byte is read       |
| No `Content-Length`, bytes ≤ 8 MiB                                     | relayed                                |
| No `Content-Length`, bytes > 8 MiB                                     | **413**; the relayed stream is errored |
| `Content-Length` that lies, bytes > 8 MiB                              | **413**; same                          |
| Malformed `Content-Length` (negative, non-numeric, float, list, empty) | **400**                                |
| Digit string too large to be a safe integer                            | **413**                                |

**`Content-Length` is the early exit, never the security boundary.** It saves an
upload and a Rails invocation in the honest case. The ceiling itself is held by a
byte counter on the stream, which is what makes a chunked, undeclared or lying
body equally bounded.

**Oversized means the upstream cannot finish.** Past the ceiling the relayed
stream is _errored_, not truncated — Rails receives a broken request body rather
than a short one it might mistake for complete. Edge answers 413 regardless of
what Rails replied, including a 2xx to the fragment it saw.

**A length Edge cannot believe is refused, not ignored.** Silently ignoring a
`Content-Length` that cannot be parsed is how an unrestricted proxy gets reintroduced by
accident.

**Nothing is buffered.** `request.arrayBuffer()` must never be introduced here;
memory stays bounded by one source chunk whatever the upload size. The counter is
a pull-driven `ReadableStream` over a reader, not a `TransformStream` pipe:
`pipeThrough` on a half-duplex request body behaves differently between workerd
and undici, and this relay has to behave identically in production and under
Vitest. One chunk read, one chunk enqueued has the same semantics in both, and
gives backpressure for free.

8 MiB is provisional — far above every current Rails surface, chosen to bound
blast radius rather than to be tight. Lower it when telemetry shows the real
distribution; the boundary tests (`limit - 1`, `limit`, `limit + 1`) move with
the constant.

### Runtime-level rejections

A malformed `Content-Length`, or a `Content-Length` conflicting with
`Transfer-Encoding`, is a request-smuggling vector that the HTTP server in front
of this Worker normally refuses before any Worker code runs — workerd does not
expose such a request to `fetch`, and neither does undici under the test harness.
The checks in `rails-body-limit.ts` are therefore a second line, reached only
where a caller constructs the `Request` directly (as the unit tests do). They are
tested at that level rather than over the wire, because no HTTP client can
produce the request that would exercise them end to end — which is the placement
rule in `AGENTS.md`.

## 3. Logout path ownership

Four exact paths are Rails-owned:

```text
/sign/out
/sign/out/
/sign/out/complete
/sign/out/complete/
```

Both spellings, because a browser reaches either one and both must clear the
Rails session. Before this, `/sign/out/` fell through to the application — which
renders a page and, per ADR 007, cannot issue or delete a cookie at all. The user
saw a plausible document while their session cookie survived.

**Never make this a prefix.** `startsWith('/sign/out')` would hand Rails
`/sign/outside` and every future `/sign/out/<anything>` Rails does not serve,
turning an ownership table into a wildcard and making the Edge table a standing
promise about routes only Rails can see. These stay application-owned and are
asserted as such:

```text
/sign/outside
/sign/out/other
/sign/out/complete/extra
/sign/out//
/sign/in
```

**No trailing-slash alias for the canonical URIs.** `/.well-known/jwks.json` and
`/csp-violation-report` keep one spelling each. Neither is typed by a human or
rewritten by a browser; `/.well-known/jwks.json/` and `/csp-violation-report/`
stay application-owned.

The same four logout paths appear in `isAuthPath` (`worker.ts`) and in the
`sign_out` route class (`rails-dispatch-log.ts`, `request-log.ts`), so the
trailing-slash spelling is neither a cheaper auth path nor a differently-labelled
one. The rate-limit _policy_ is unchanged.

## 4. What this boundary does not touch

Unchanged by ADR 023, and not to be changed alongside it: rate-limit policy, OIDC
path ownership, the public-surface RPC contract, cookie stripping, `Authorization`
stripping, Rails response passthrough, `redirect: "manual"`, SSRF protection, the
Host allow-list and its 421, the CSP nonce contract, and service worker
ownership.
