# ブラウザから呼べる内部 API とデバッグ機能の安全性

## 画面に入口がない機能も攻撃対象になる

ブラウザへ配信したコードと、ブラウザから到達できる API は、利用者が調査して直接呼び出せるものとして設計する。
ここでいう「非公開の API」は、画面から使わせる予定のない内部処理や開発用の呼び出し口を指し、言語の `public` / `private` 修飾子の意味ではない。
画面にボタンがない、通常の操作では呼ばれない、関数名を公開していないという理由で、安全だと判断してはならない。

利用者は開発者ツールでクライアントの状態や処理を変更し、画面の制約を経由せずリクエストを送れる。
クライアントの関数を実行できること自体を、サーバー上の権限を得た証拠として扱ってはならない。
保護すべき境界は、改変されたクライアントや直接送信されたリクエストでも、不正な操作をサーバーが拒否できることである。

## 実装時のルール

- ユーザー権限の変更やアカウント作成などの操作は、処理を所有するサーバーで毎回、認証と操作対象に対する認可を検証する。
  クライアントが送る権限、ユーザー ID、開発用フラグを信頼せず、画面側の判定だけで許可しない。
- 必須の認証ヘッダーの欠落や不正な形式の認証トークンを、安全側に拒否する。
  ヘッダーを省略した場合に認証を迂回する分岐や、トークン検証の失敗時に権限を与えるフォールバックを作らない。
- 入力の型、許可する項目、値の範囲をサーバーで検証する。
  NoSQL を使う処理では、利用者が送ったオブジェクトや演算子をそのまま検索条件に渡さず、許可した入力から条件を組み立てる。
- エラー本文、ステータス、ヘッダー、応答時間の違いが、権限のない利用者にアカウントの存在や属性を推測させないか確認する。
  NoSQL インジェクションによるブラインド探索など、応答の差だけを手掛かりにする攻撃も対象にする。
- デバッグ用の関数、グローバル変数への操作口、テスト用アカウント作成、認証や認可の迂回機能を不用意に追加しない。
  秘密情報や管理用の認証情報をクライアントコードに置かない。

Edge が Rails へ中継する処理では、実際の操作を所有する Rails 側でも認証と認可を検証する。
境界の詳細は [Edge と Rails の信頼境界](edge-rails-proxy-trust-boundary.md) を参照する。

## 開発用コードをデプロイに混入させない

開発用の機能が必要な場合は、用途と削除条件を明記し、本番のビルドとルート登録から除外する。
画面から隠す、URL を知られないようにする、ブラウザで変更できるフラグで無効化するだけでは、本番からの除外にならない。
不要になったコードは削除する。

デプロイ前には、ソースだけでなく、本番設定で生成したクライアント資産と Worker の成果物を確認する。
デバッグ用の呼び出し口、開発用ルート、認証迂回の分岐、テスト用データ、秘密情報が残っていないことを確認し、ビルドで消える想定だけで済ませない。
未使用コードの検出や圧縮も、アクセス制御の代わりにはならない。

## レビューと検証

- 画面の操作順序や表示制御を無視して API を直接呼んでも、権限変更やアカウント作成を不正に実行できないか確認する。
- 未認証、権限不足、別ユーザーの操作対象、必須ヘッダーの欠落、不正な形式の認証トークン、不正な入力を検証する。
  拒否応答だけでなく、拒否した操作によってデータが変更されていないことも確認する。
- 開発用機能が本番成果物に含まれず、開発用エンドポイントも本番で利用できないことを確認する。

HTTP 応答の検証は各 unit の `api/` に Hurl で置く。
内部の認可判定や不正な操作で状態が変わらないことの検証は、その処理を所有する側で行う。
ブラウザの実際の動作が必要な検証は `e2e/` に置き、同じ応答の検証を重複させない。

この文書は実装とレビューのルールであり、現在のコードや本番環境に対するセキュリティ監査の完了を示すものではない。
